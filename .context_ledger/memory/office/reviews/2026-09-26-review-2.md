# 2026-09-26 (second session) — the run that settled on a folder sharing the goal's name

**Deliverable: a diagnosis, no product change.** The supervisor's direction, mid-session, moved the fix
somewhere I could not land on my own word: *"the bug isn't 'the matcher needs a .git check' … the actual fix
is in how the engine generates and weighs alternative states before settling."* That is a change to when the
engine may declare a goal settled — its central contract, its event stream and its budget — so per the
standing findings policy (fix safe, flag architectural) this report carries the finding and the designed
next step, and the row is in the backlog. Nothing under `ti_matrix/`, `server/` or `app/` changed.

## What was reported

The supervisor ran the files world with a goal naming a repository by its folder name, and the app answered
with **the same-named folder in the home directory** — a runtime folder holding a database, sessions and
uploads — when the actual git checkout sits one level down under `Dev/`. Paraphrased rather than quoted:
the goal's own words name a sibling project, and this repo's standing convention keeps other repositories'
names out of committed files. The goal string, the literal paths and the run itself are in this machine's
app library at `runs/20260926-120837-b1d5` (untracked), which is the primary evidence below.

## What the run did — from its own saved events

The run was a real model run, not the rule-based seat: `deepseek-flash` via DeepSeek. Its whole search was
**one fan, three probes, two evaluations, and a settlement**:

- three candidates, all aimed at the home directory: `recall(…)` about earlier runs, `list_dir(path=.)`, and
  `stat_path(path=LocalMind)` — a relative name resolved under the world's root, which is home;
- `recall` came back "nothing in earlier runs matches"; `list_dir(".")` returned home's 158 entries;
  `stat_path("LocalMind")` returned `<home>\<name> — dir, 0 bytes, modified 2026-09-20 22:20`;
- the evaluator marked **both** of the last two `done` at `progress: 1.0`, with reasons that read (name
  elided) *"list_dir of \<home\> shows a \<name\> directory, locating the repo at \<home\>\\<name\>"* and
  *"stat_path confirms \<name\> resolves to \<home\>\\<name\>, a directory"*;
- the engine selected `list_dir(path=.)`, emitted `done`, answer `<home>\<name>`. Total: 2 model calls, 33s,
  and the green ANSWER card the supervisor saw.

Note what the second reason claims: a `stat_path` that reported **"a directory"** was recorded as
confirmation of **"the repository"**. The goal's own word — repo — was never observed anywhere in the run.

## Why the engine accepted it

Two mechanisms, and neither is about path matching.

**1. A settlement ends the run on the fan that claims it, so no competing candidate is ever generated.**
`StateEngine._steps` computes `best_done = ranked_real[0][1].done` and, when it is true, emits `done` and
returns (`ti_matrix/search.py:363`). The machinery for holding alternatives exists — immutable `AgentState`,
`backtrack`, node/parent links on every event, and `DESIGN.md`'s "the search can then hold several states at
once, compare them" — but it is only ever *reached* through failure: `NothingImproves` backtracks when a fan
fails to beat the state, and a claimed settlement bypasses that check entirely via `best_done`. So the search
has no success path that weighs a second route. In this run the alternative the goal actually wanted was
never proposed, never probed, and appears **nowhere in the event record at all**.

**2. The guard is not the guard the design claims.** `DESIGN.md` (The loop) states: *"a failed probe never
counts as progress, and `done` requires an answer grounded in facts."* The implementation
(`ti_matrix/model.py:124-129`) checks two things: the outcome succeeded and was not predicted, and
`ev.answer.strip()` is **non-empty**. Nothing checks that the answer is grounded in anything. The guard's own
comment says "done needs a grounded answer"; the code tests for a *present* one.

I ran the engine against a fixture to see how far that gap reaches — a home directory holding a folder that
shares the goal's name and has no `.git`, plus the real checkout under `Dev/` that the goal wanted. Driving it
with the real run's own evaluator output:

```
--- name match (the real run's evaluator output)
    events:  state -> candidates -> probe -> evaluation -> selected -> state -> done
    fans:    1,  probes: 1
    settled: True    answer: <fixture>\acme
    the real repo's path appears in the event record at all: False

--- fabricated answer (appears in no observation)
    events:  state -> candidates -> probe -> evaluation -> selected -> state -> done
    fans:    1,  probes: 1
    settled: True    answer: C:\Users\someone\Nowhere\acme
    the real repo's path appears in the event record at all: False
```

The second case is the sharper one: **an answer naming a path that appears in no observation settles the
run**, and the app draws it as verified. `app/renderer/core/decisions.ts:331` returns
`{ text: last.answer, verified: true }` for a `done` and `verified: false` only for a synthesised answer, so
the one distinction the UI draws — settled versus guessed — is decided by which event arrived, not by
whether the answer was ever established.

Worth stating plainly because it is *not* a defect: the belief readout is honest about itself. `trust.ts`
describes the number as "the model's own belief", `App.tsx:327` prints its mean, and `progress` is carried
straight from the evaluator with no penalty — which is exactly what the supervisor suspected. The problem is
not that the number lies; it is that the engine treats the number as a settlement.

## The three questions the earlier session left open

- **"Does the matcher stop at the first name hit rather than enumerating siblings?"** There is no matcher —
  this was a model run, and the rule-based seat's loose `named` test is a separate, already-filed case
  (`B-2026-09-26-3`). The equivalent happened anyway: all three actions in the one fan were rooted at the
  same directory, no search was proposed, and the one action that enumerates names cannot find a directory
  at all — `find_files` filters to `is_file()`, so a `contains` search for the folder's name returns "no file
  under … has 'acme' in its name (3 paths searched)". **Nothing in either seat ever enumerates candidate
  directories.**
- **"Is there any signal distinguishing 'a folder named X' from 'a git repo named X'?"** No — `stat_path`
  reports `dir, 0 bytes`, `list_dir` reports `📁 name`, and no observation mentions git. But per the
  supervisor's direction this is *not* where the fix goes: teaching the world to recognise repositories
  swaps one shortcut for another. The engine should weigh the alternatives, not be told what one looks like.
- **"Does belief 100% come purely from a name match, with no confidence penalty?"** Yes, and there is no
  mechanism to penalise it: `progress` is the evaluator's number, the guards only zero failed or predicted
  outcomes, and the engine has no representation of "an alternative was never considered".

## What to do next

The fix belongs in how a settlement is earned, and the smallest shape that matches the supervisor's framing
is a **challenge round**: a fan that claims `done` does not end the run — the engine forces one more
propose/probe/evaluate cycle with the claimed action pruned, so the search must generate something *other*
than the answer it already has. If that round produces nothing better, the claim has survived a challenge
and settles. If it produces a different claim, the two compete, and the run must keep going rather than pick
one and paint it 100%.

Design constraints found while reading, for whoever lands it:

- **Budget.** A challenge round costs up to two model calls on top of the fan that claimed `done`. The
  existing `answer_reserve` precedent (`TerminalContext.answer_reserve`, and `BudgetExhausted`'s
  `calls + 2 + reserve`) is the pattern to follow; a challenge that cannot be afforded should settle with
  the claim marked *unchallenged* in the record rather than silently skipping it.
- **The empty-fan trap.** After a claim is applied, `state.progress` is 1.0, so a challenge fan scoring
  lower would trigger `NothingImproves` → `backtrack`, and a settled run would keep walking instead of
  settling. The challenge round needs to be recognised by the loop, not squeezed through the ordinary
  no-improvement path.
- **The event stream is the UI contract.** Extra `candidates`/`probe`/`evaluation` events are fine — the
  renderer folds them as more search — but a new event *kind* or a new stop reason means
  `app/renderer/core/` and the visual checks. Prefer reusing the existing kinds.
- **One open decision for the supervisor:** when a challenge produces a second claim, does the run (a)
  prefer the better-scoring claim, (b) keep searching until one claim survives a challenge unopposed, or
  (c) stop as `settled: false` and report both? (b) is the most faithful to "belief should split or stay low
  until the agent reasoned about which one satisfies the goal", and it needs the budget to bound it.

## Also found, not fixed — recorded in `tasks/parking-lot.md`

- **A fact is cut to 320 characters as it enters the state** (`state.py:14`, `_FACT_CHARS`). Home's listing
  was 3,878 characters, so once it became a fact the model could no longer see the entries that mattered —
  the name it settled on survived only because `stat_path` had echoed the resolved path back in a short
  observation. A run that lists a large directory and decides later is reasoning over a fragment.
- **`find_files` cannot match a directory**, so no goal naming a folder can be satisfied by search — only by
  opening directories one at a time.
- **`stat_path` reports a directory as `0 bytes`**, which is an artefact of the platform and reads as
  "empty" to a model using it as confirmation.

## The small-viewport question, answered from the CSS

The supervisor's reading is right — the earlier "designed by a backend developer" impression was a small
window, not a design fault, and the layout already carries breakpoints at 1180/820/720/700px. What is
genuinely missing at small widths, from `app/renderer/styles.css`: the **top rail never wraps or shrinks**
(`.rail` is a single non-wrapping flex row holding six metrics, the run controls and the window buttons), the
**inspector row's three columns have minimums summing to ~640px** (`.inspector`, line ~574) with no
breakpoint below the stage's own 1180px collapse, and **the pane grid's minimums (`420px + 360px`) only
collapse at 1180px**. Below roughly 700px those three overflow rather than reflow. Not fixed: it is a layout
change needing its own render at 360/768/1280 to verify, which this session did not run.
